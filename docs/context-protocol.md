# Host task capture context protocol

This protocol validates the host demonstration of a task that blocks, receives a nested interrupt-driven completion, resumes on another modeled CPU and returns. It is a protocol and continuation experiment, not a kernel scheduler or IRQ-safe writer.

The [single-CPU hardware interrupt replay](async-interrupt-replay.md) uses the same protocol with an optional `--single-cpu` capture. Its AArch64 image receives a physical timer IRQ and a higher-priority nested SGI, then checks the complete target-recorded transcript. Task scheduling remains an explicit continuation model.

## Wire records

All scalar fields are unsigned and little-endian. The file begins with eight bytes: ASCII `OSRC`, followed by the 32-bit format version 1. Each record has a 12-byte header containing 32-bit kind, site and payload byte count, followed by that payload.

The task demonstration has this record sequence:

| Kind | Site | Payload |
| --- | --- | --- |
| BEGIN 1 | 0 | 64 ASCII bytes of the task region header SHA256 |
| INPUT 2 | 100 | CPU count, selected task ID, one current task ID per CPU |
| INPUT 2 | 110 | Initial available credits and demand |
| CONTEXT 6 | Per boundary | Eight 64-bit fields described below |
| OUTPUT 4 | 330 | Expected remaining credits and return value |
| END 5 | 0 | Empty payload |

There are 13 CONTEXT records in the supported scenario. A two-CPU capture has 8 file-header bytes, five non-context records contributing 60 header bytes and 128 payload bytes, and 988 context-record bytes, for a total of 1,184 bytes.

## Context fields and identity

Each CONTEXT payload has `sequence, cpu, context, parent, task, operation, a, b`, in that order. Sequences start at zero and increase once per context event. They are generated by the externally serialized host writer; this global sequence is not a proposed scalable SMP ordering mechanism.

Task IDs are nonzero and below bit 63. They represent lifetime-specific identities supplied by the caller. IRQ IDs have bit 63 set and are unique within a capture. The initial tasks must be distinct across CPUs, and the selected task must be running on exactly one configured CPU.

The `task` field identifies the base task on that CPU, including the task interrupted by an IRQ. It need not be the selected task. The `context` field identifies the active task or IRQ, and `parent` identifies an IRQ's immediately interrupted context; ordinary task events have parent zero.

IRQ ENTER records describe the context after pushing it. IRQ EXIT records describe the context before popping it. SWITCH records describe the departing task context; `a` and `b` contain the previous and next task IDs. These conventions make parentage and switch ownership independently checkable offline.

## Supported operation meanings

| Operation | a | b |
| --- | --- | --- |
| BLOCK 1 | Wait object ID | Object generation |
| SWITCH 2 | Previous task ID | Next task ID |
| IRQ ENTER 3 | 0 | 0 |
| IRQ EXIT 4 | 0 | 0 |
| DEVICE VALUE 5 | Device input object ID | Observed value |
| MEMORY EFFECT 6 | Completion object ID | Expected post-handler value |
| WAKE 7 | Wait object ID | Object generation |
| TASK RETURN 8 | Return value | 0 |

The model supports up to four configured CPUs and four nested IRQs per CPU. It rejects mismatched current task IDs, switches inside an IRQ, a task running on two CPUs, resuming the selected task while blocked, invalid IRQ exits, mismatched wait generations and return with unfinished interrupt contexts. Any error or buffer overflow makes capture failure sticky. Finish requires the selected task to have returned.

## Fixed continuation schema

The task exporter supports these sites and operations in order:

```text
200 BLOCK
210 SWITCH away from the selected task
220 outer IRQ ENTER
230 outer DEVICE VALUE from object 9
240 nested IRQ ENTER
250 nested DEVICE VALUE from object 10
260 nested MEMORY EFFECT on completion object 1
270 nested IRQ EXIT
280 outer MEMORY EFFECT on completion object 1
290 WAKE the matching wait object and generation
300 outer IRQ EXIT
310 SWITCH back to the selected task
320 TASK RETURN
```

The original handler helper applies the device input with saturating addition. The task continuation blocks until sufficient credits exist, then consumes its demand and returns that amount. Generated replay calls these original helpers at supported boundaries, verifies intermediate effects and checks the final output. Expected effects are never assigned directly to the reconstructed completion state.

The C harness uses continuation boundaries rather than restoring a saved native stack. It executes no real scheduler, hardware IRQ or host CPU migration. A real kernel implementation needs compatible context bookkeeping, reservation/commit safety, relevant object checkpoints, asynchronous effects, shared-memory observations and a matching replay environment.

## Validation and limits

The exporter rejects sequence gaps, unknown sites or operations, invalid CPU/context relationships, duplicate IRQ identities, missing device inputs or effects, mismatched return values, incomplete records, trailing events and source mismatches. Structurally valid but incorrect effect expectations or device inputs are detected when replay recomputes results and compares them.

The source fingerprint binds only `task_region.h`; it is neither a complete build identity nor an integrity checksum over trace contents. The completion object has one lifetime throughout this scenario. General object reuse, arbitrary atomic operations, SMP races and instruction-position interrupt delivery are unsupported.

The wire format and host checks are intended to establish a conservative reference before kernel-specific compression or probe removal. No overhead benefit has been measured.
